# 实现复盘草稿

以下由 AI 根据本次实现整理，是工程观察。候选人已说明亲自检查关键节点准确性，个人学习体会仍待本人补充。

## 最难的问题

一是决定哪些行为交给模型：换素材、换内容形式、重试还是停止属于业务决策；保存门槛和最终成功状态必须由程序控制。二是不能混淆“成功生成计划”和“成功执行活动”，业务步骤保持 planned，工具步骤单独记录 succeeded/failed。

## 本次处理与收获

- 初始草稿只比较费用与时间标记，最终增加方案版本、指纹及保存时重算，避免旧估算授权新方案。
- 幂等不能仅靠输出文案；测试检查真实文件字节、保存数量及零新增模型调用。
- 工具失败不是清空状态的理由，已有脚本继续保留，并通过下一次模型输入验证它确实可见。
- HTTP 适配器的测试通过不代表真实模型会正确规划；两类验证证据必须分别说明。

## LangGraph 重构观察

- 图的条件边只根据动作或终止状态路由，预算超限作为观察返回 decision，业务重规划仍交给模型。
- reducer 使用追加语义，节点必须只返回本次新增记录，否则历史会重复；通过步骤数、Trace数和检查点测试验证。
- 一次业务动作会经过 decision 和 execute_tool 两个节点，不能把图 super-step 上限直接当作业务步数上限。
- 新增检查点测试最初选中了后续检索阶段的快照：检索没有修改方案，旧的超预算估算仍然有效。修正为筛选“最新观察为估算”的快照，保留初始失败报告。
- InMemorySaver 能提供快照与历史，但不保存外部工具对象、Mock 游标或真实 API 副作用。当前不提供恢复命令，未验证故障恢复。
